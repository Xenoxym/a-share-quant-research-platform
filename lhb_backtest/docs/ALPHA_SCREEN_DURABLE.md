# 特征筛选怎样成为可接续的正式实验

E13D 建设记录，2026-10-07。当前验收状态以阶段记录和任务库为准；本页解释接口及其限制。

我们已有“给每只股票一个分数，再挑分数最高的股票”的筛选程序。本阶段让它成为可登记、可中断、可恢复和可复核的作业：换一个进程继续时，原来的候选、方向、条件、失败和已用预算仍在。它不是模型训练，也不是完整资金账户。

## 从使用者角度看一次作业

举一个四只股票的合成例子。每个决策日输入四行 X；每行有股票代码、当时已知的特征及可用时间。我们提前声明四个候选：特征一、特征二、两者交互项，以及一个保留探索机会的候选。方向 +1 表示优先高分，-1 表示优先低分，两者都只买入股票。可选条件如“特征二大于零”也只能读取当时的 X。

程序按声明的 K 挑股票。K=2 时，每只占两个固定名额中的一个；只有一只符合条件，另一个名额留现金。如果已经选中的股票没有成熟 Y，该窗口收益显示未知，不能换成别的股票、重新分配权重或悄悄删除那一天。

Y 是提前声明的实际执行窗口收益率，标签起点/终点须等于决策表的执行起点/目标终点。它不是固定五天，也不一定是周一开盘至周五收盘。诊断截止时间之后才知道的结果，以及保留历史区间中的数值，不参与筛选收益计算。保留历史区间已经被看过时，它仍不是新的未见样本。

## 数据和程序怎样流动

```mermaid
flowchart LR
    A[保存候选与有限预算] --> B[七类文件与SHA登记]
    B --> C[冻结源码与环境]
    C --> D[共享资源槽与启动握手]
    D --> E[只处理成熟开发窗口]
    E --> F[完整筛选表和终端收据]
    F --> G[重放冻结程序并逐项核对]
    G --> H[收取到任务库]
    H --> I[下一阶段训练和原生账户]
```

七个输入角色是 `registry`、`assembly_values`、`assembly_missing`、`assembly_definition`、`assembly_receipt`、`decisions`、`labels`。每个文件须提供项目内相对路径、字节数和 SHA256；路径不能逃出授权数据/研究目录，也不能经符号链接绕行。组装引用收据绑定数值、缺失、定义文件及注册版本，不证明此前生成数据的算法实际运行过，也不认证供应商历史。

## 怎样调用

使用既有 `tools/research.py register/run/recover`，提案 `kind` 为 `alpha_screen`。Python 入口仍是 `Research.register`、`Research.execute` 和 `Research.recover`。内部只允许 `alpha_batch` 和 `alpha_screen` 两种已知协议选择相应冻结执行器；提案不能填写任意模块名称或使用 free eval。

提案外层包含 `kind`、`hypothesis`、`expected_observation`、`falsification`、`inputs`、`spec`，可附 `timeout_seconds` 和严格资源限制。

```json
{
  "kind": "alpha_screen",
  "spec": {
    "schema": "registered-alpha-screen-v1",
    "screen": "这里填写完整的 development-screen-v1 对象，不能使用此占位字符串",
    "budget": {
      "max_input_bytes": 1000000000,
      "max_task_channel_intents": 48
    }
  }
}
```

这是结构示意，不能直接登记。完整 `screen` 包括日期、目标、方向/条件候选、家族及探索名额、K、覆盖要求和矩阵上限；其字段由 `ScreenSpec.from_dict` 校验。可运行的合成构造见 `tests/test_alpha_screen_registration.py`，不会读取真实行情或训练新策略。

## 重启之后哪些东西还算数

任务本身已有正式作业次数上限。第一个筛选登记还固定该任务的累计候选名额；之后每次登记在同一个数据库事务内核对累计数，不允许更换预算以清零。一个特征分别试正方向、负方向或不同条件，是多个候选意图。登记失败后的冻结错误、运行失败及取消都保留并计数。

修改显示名、假设文字或文件列表顺序不会重新启动原实验。影响结果的候选身份、方向、条件、规则或源码版本变化会形成不同定义，仍要消耗名额。重复调用已启动作业被拒绝；`recover` 收取原结果，不重新计算。资源不足发生在启动之前时作业保留为 planned，已登记的候选预算依然占用。

父进程停止观察或收取锁暂时忙时，资源槽保留确切 PID/创建时间和启动记录。只有确认原 worker 已退出，才核验终端收据并提交结果。没有收据时不能猜测已完成，也不能自动重跑。Windows 原子解释器启动握手和既有严格子进程规则继续使用。

## 输出到底是什么

| 文件 | 回答的问题 |
| --- | --- |
| daily.json | 每天哪些股票符合条件、缺失多少、RankIC 的诊断值是什么？ |
| selections.json | 当时按 X 选中了谁、分数和固定权重是多少？ |
| windows.json | 固定名额的毛收益、现金比例和端点净值是否可知？ |
| trials.json | 每个候选是否达到数据要求、为何晋级或未晋级？ |
| redundancy.json | 特征排序的重复程度，预算内计算了哪些配对？ |
| attempts.json | 事前声明的全部方向/条件意图和执行状态 |
| diagnostic_receipt.json | 实际消费的数据指纹、纯程序身份及诊断边界 |
| manifest.json | 输出文件与登记、源码及候选清单的 SHA 绑定 |

纯程序收据仍如实标记其本身为进程内 API。外层任务结果使用 `registered_alpha_screen_execution` 和 `registered-alpha-screen-audit-v1` 表示持久执行与核查，不把纯 API 的自述改写成持久能力。

第一次数值核查会从不可变的源码副本重新运行同一个筛选算法，比较全部表、诊断收据和候选状态。隔离导入不读取或写入冻结目录的字节码。核查记录绑定输入、输出、整个源码库存和核查代码版本；后续恢复/提交/复核也要检查。它是同算法重现，可能保留共同算法错误。手工反例测试另行验证选股和现金/未知标签规则；这仍不能代替独立市场数据认证或账户核查。

筛选的累计毛收益与端点回撤只用于便宜地淘汰候选；没有分红、费用、涨跌停、停牌及日内资金路径，所以不是年化账户收益或完整最大回撤。晋级表示值得进入下一层实验，不表示有效策略。

## 接下来为什么要接训练与账户

下一阶段 E16D 将已有的训练接口也接到同一持久链。随后有限 E19 实验才能在共同股票池与执行口径下，对比价格量、涨跌停形态、龙虎榜、财务及市场信息，并尝试多个模型；最终用原生账户的收益和回撤判断，保留小市值、固定组合和费用反事实对照。当前工程核查不宣布任何新策略盈利改善。

## 当前资源和核查边界

资源槽、采样RSS、线程和超时监测覆盖冻结worker。父进程收取时同步重放完整筛选；恢复、提交和复核也可能重放，其计算目前没有独立资源槽或RSS/超时监测。正式工程验收仅按登记的小批和外部测量运行；不能把worker观测解释为全链资源受控，不能开启无上限并行核查。后续应把核查执行纳入同一资源调度。

全表、诊断收据、候选清单和组装引用使用规范化JSON进行严格比较：true/false与数值不同，整数1与浮点1.0也不同；字段顺序不影响比较。意外类型变化不能只靠重新封好SHA而通过。
