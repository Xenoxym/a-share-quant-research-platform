## 3. 哪里最浪费：我的排序和依据

这个排序依据工作记录与因果链。**它是对返工优先级的判断，不是有账单支持的 Token 排名。**

### 第一：反复检查外围流程，比推进研究本身更重

我们需要保留数据来源、代码版本、训练边界和账户核查。但实际过程发展成了：为启动写辅助脚本，检查脚本，修检查脚本，保存新的检查范围，再让两个代理复查，随后主程序重新核对同一批文件。

证据很具体：R32S的一次元数据收尾中，主程序再次核对了302份原件；前一阶段的结果登记又核对347份原件。它们有保存历史的作用，但不应让每次路径、报告或登记修正都承担相似的完整核查成本。

本次24小时内，阶段目录共有**2179个顶层文件的修改时间落在范围内**，其中**484个Python文件，按原字节去重为475份**。修改时间包含生成、复制和改写，不能把这些数字说成“新写了这么多产品模块”。它仍反映了辅助文件与流程变体过多。

保存的意见中，按“复核者＋完成时间”去重有**309条复核意见记录**。有开始时间或耗时的记录，其区间合并后覆盖约**459.0分钟**。这不是独立会话数或浪费分钟数：同一意见可能被重新登记，期间有思考和等待，而且与其他工作重叠。它足以提醒我们检查复核范围；不足以当作账单。

**应改为：同一代码基线保留一次有效检查；本轮只复核真正改变的部分。模型、数据时间边界或账户规则改变时，仍保留对应的完整科学检查和独立复核。**既有验收要求不能靠口头省略，要先让可复用的检查协议支持这种范围区分。

### 第二：我自己引入的接线错误，触发了越来越大的修复链

| 具体错误 | 为什么可避免 | 应怎样做 |
|---|---|---|
| 同一个时间用纳秒与微秒保存，被直接当成不同数据 | 比较了表示形式，没有先统一时间含义 | 小样本先验证时区、精度、股票键和日期，再做全量 |
| 生成器把15:30错误改成15:00 | 字符串改写影响了真正的信息可用时间 | 对信息时间使用明确字段；检查一个完整例子的输入和输出 |
| 已成功计算64列，装配函数又触发完整数值核查 | 原执行流程已核查，调用方没有识别装配会再次核查 | 明确区分“使用已核查结果”与“重新做完整数值核查”；引用的版本和内容必须一致 |
| 启动辅助代码先保存计划，又检查尚不存在的预算/会话文件 | 启动顺序不成立 | 一个稳定入口完成初始化；失败状态能恢复，不为每次失败再造一套入口 |
| 结果登记的相对路径和导入清单不一致 | 辅助代码增多，入口约定不统一 | 维护少量公共模块，用真实最小执行检查入口，而非仅检查语法 |
| 报告生成假设安装了`markdown`，实际未安装 | 没复用项目已经可用的`mistune` | 先确认现有依赖；复用现有渲染工具 |
| 改文档时调用已完成阶段的时间门槛，随后又用过严的字符串检查 | 检查用途与当前任务不匹配 | 文档核查只检查链接、事实和生成结果，不恢复旧执行阶段 |

64列那次外层操作约35分钟后失败，公式进程约12.4分钟。**二者相差的22.6分钟包含准备、必要核查和重复核查，不能全算成重复核查的浪费。**但是源代码明确证明装配入口再次调用完整`audit_output`，这个重复边界应该消除。

另一个小例子：预测期接线的3版私人草稿，保存的准备耗时相加约**29.6分钟**；最终仍未形成完成且实际测试过的实现。第三版超过600秒预算。这不是全部无用，但说明“先写很大一份，再逐层封装检查”的实施方式不适合有限额度。

### 第三：研究顺序偏离了你要的产出

64列特征原本应先成为模型可用的数据，再比较“原68列”和“加入64列后的132列”。我额外把“每列单独选10只股票是否赚钱”放在前面，花时间构建、修补这条筛选路径。

**单列独立选股没赚钱，不等于这列对多变量模型没用。**这条诊断可以研究，但不应成为全部新特征进入模型的强制门槛。尤其本次它还有日期错误，使后续工作更绕。

下一阶段要用可交付的完整小路径衡量进展：先把预测期新列接入，做小样本真实执行，随后完成同模型、同账户规则的68列与132列对照。额外诊断放在可独立比较的分支。仍保留广泛模型、龙虎榜、板型、财务、组合特征和清单外研究，不以减少模型范围换取表面效率。

### 第四：大上下文、重复阅读和难懂报告，扩大了语言模型处理量

多轮复核反复读取大量旧记录；工具输出过大而被截断，又需补读；报告以内部编号和登记状态组织，读者无法理解，随后重写。这些都会增加处理量。

本次成本复盘开头也有一次搜索过宽、输出截断；我已改为定位文件、读取所需字段。本次没有再派代理，也没有重跑模型、数值核查或CI。

**文件数量、散列计算次数、运行分钟数，都不能换算为 Token。**只有实际传给模型和模型生成的内容等用量记录才可用于核算，缓存和额度计费规则还会影响最终扣除。

## 5. 怎样避免：从下一阶段开始执行的准则

| 准则 | 具体做法 | 如何知道有没有改善 |
|---|---|---|
| 先确定这一批要回答的问题 | 写清输入、对照、最终收益/回撤输出和有限计算预算；外围建设必须服务于它 | 阶段结束列出实际新增模型、账户、可用数据路径，而不是只列验收文件 |
| 先跑一个完整小例子 | 覆盖数据→特征→模型→账户；优先真实执行，包含缺输入、缺成熟收益和现金反例 | 大数据启动前发现接口与时间问题 |
| 少量稳定入口 | 将反复使用的操作归入公共模块；不按每次尝试复制出一套脚本 | 新辅助脚本数量、重复入口和修补次数下降 |
| 复用已有效的检查 | 不变的基线引用旧证据，变化部分做针对性复核；最终新方法和账户仍须独立检查 | 同一数据/代码版本的全量重检次数可解释；无条件重复为0 |
| 限制返工链 | 同类接线失败两次后，先简化/换实现路径；不得不断开新预算重复同一种做法 | 每批记录失败原因、返工轮数与实际可用产出 |
| 让复核尽早发现科学错误 | 复核共同日期、标签成熟、缺失输入与现金处理，而非主要检查文件是否对齐 | 此次“56缺收益、8现金通过”的最小反例进入检查 |
| 减少无关上下文 | 代理只收到问题、变动、必要证据与约束；工具先检索再取字段，避免整包输出 | 普通单次输出目标约1500 Token以内；较大输出有具体用途，代理交接不重复整段历史 |
| 报告一次说清楚 | 先说本轮问题、实际做法、结果、未完成内容，内部细节放末尾 | 用户能回答“用了什么、实际跑了什么、下一步是什么” |
| 分开记真实用量与替代指标 | CLI若返回`usage`就保存真实字段；桌面用量没有接口时记未知。工具输出量只能作替代观察 | 不再用分钟、文件数或工具输出估算值冒充账单 |

这些准则已作为项目入口的补充保存，**没有删掉旧证据、修改历史预算、跳过既有验收，或把尚未修复的代码说成完成**。本次是成本复盘和工作准则更新，不是新的模型或收益验收。

## 6. 哪些保留，哪些现在改变

保留：训练时只能使用当时可知的数据；成熟标签边界；完整账户；必要的反例；有效失败记录；不同模型/特征的广泛探索；与小市值等对照比较；收益和回撤作为重要成果标准。

改变：每个小步骤都重新封装、复制、复核的做法；先造大草稿再验证能否跑的做法；将单列盈利当作模型输入门槛的做法；把内部验收状态当成面向你的主要报告内容的做法。

下一次研究优先交付“新特征能真正进入模型、并产生可比较账户结果”的完整路径。日期诊断错误仍需修复，132列的容量限制仍需处理，旧排队任务仍未执行。本次复盘没有为了显得进展快而启动新的计算。

## 7. 为什么这些检查会反复触发？是你要求的吗？

**你的质疑成立：自动测试应该复用，文件校验也应该自动完成。这里反复消耗Token的，主要是我围绕这些操作增加的写代码、代理阅读、复核和登记，而不是Python计算校验码本身。**

你要求高质量、可追溯、自动推进；这些要求并不等于每个小步骤都要重走一套完整验收。我把研究结论的复核、软件测试和辅助文件的登记捆得过紧。这是我选择和实现的流程，不应把复杂程度归因于你的授权不足。

### 原本应区分的四件事

| 事情 | 它回答什么问题 | 是否需要AI持续参与 |
|---|---|---|
| pytest和真实小样本试运行 | 改动有没有破坏已知行为，整条接线是否能运行 | 程序自动运行；失败后才需要定位原因 |
| 文件/配置校验码，也就是我说的指纹 | 本次用的是不是那份代码、数据和配置，文件有没有改变 | 程序自动计算和比较 |
| 方法与结果复核 | 标签有没有未来信息，比较是否公平，收益结论是否成立 | 新方法、重要账户结论需要有针对性的独立检查 |
| 归档 | 把本次配置、版本、模型、分数、账户和结果关联起来 | 应由稳定程序写入，通常不需要为每次归档再写脚本 |

**指纹相同也可能是同一份有bug的代码。pytest全通过也可能遗漏某种科学错误。两者都不能代替“这次比较方法是否合理”的判断。**本次64列的错误就是：既有工程检查未覆盖“同一未成熟周，有输入的方案退出、没输入的方案按现金通过”的共同日期反例。

### 现在具体什么情况会触发？

| 情况 | 我们现有流程实际会做什么 | 必要性判断 |
|---|---|---|
| 登记一个新模型/公式/账户实验 | 固定参数、输入、代码版本，检查预算与数据边界，执行并保存结果 | 核心有必要；应由公共入口一次完成 |
| 更改已被绑定的代码或文件 | 文件内容不再与原复核记录对应，拒绝沿用原接受意见 | 防止用旧意见证明新代码有必要；不表示整仓库都需要两名AI重读 |
| R32SC辅助阶段准备启动或收尾 | 读取计划、预算、任务状态、旧准备记录、两名复核意见及源码清单，并检查文件是否一致 | 范围过大，很多旧内容不应每个小步骤重新审查 |
| 任一复核者晚于规定时间 | 该辅助入口要求两份accept都在同一400秒窗口内完成；超时不能通过该入口 | 有限预算必要；把“意见是否有效”与“是否准时”绑死，导致额外登记和复核，设计不合理 |
| 原阶段时间预算已经结束 | 老辅助入口拒绝执行；为完成剩余元数据又出现新的专用恢复代码和复核 | 计算到期停止必要；普通文档/归档不应依赖旧计算入口的运行时钟 |
| 仅改报告或登记路径 | 部分旧辅助入口也可能检查完整旧范围 | 这通常没有必要；检查事实、路径和生成结果即可 |
| GitHub发生push、PR或手动启动 | 自动运行Windows/Linux软件测试和打包检查 | 必要的发布回归；不需要AI在测试运行时持续讲话或读取全部日志 |

这些条件可以在`r32sc_common_08.py`的`checked()`、`source()`、`plan()`里直接看到，不是模糊推测。其中`source()`还计算当前整个src范围的内容清单，并检查前置记录和大输入。

我把临时助手也当成严格的验收对象，又为每次修复新增版本，造成下面的循环：

```text
辅助脚本出了问题
  → 改脚本或登记文件
  → 原复核范围不再对应
  → 再准备冻结范围、请两个代理重读
  → 登记/恢复脚本又需要修改
  → 再次改变范围，再复核
```

**防止结果混用是合理目标；把每次微小修补都扩大成这一循环，确实没有必要。**这些旧辅助入口仍在项目里，本次只解释和统计，没有把它们声称为已经重构完成。

## 8. 指纹到底是什么？GitHub又在检查什么？

### 指纹用一个具体例子解释

假设准备训练一个模型，我们记录：数据快照A、训练日期、132列特征的定义、随机森林参数B、代码版本C。程序把这份配置计算成一段校验码，作为这个实验的内容标识。

以后看到一个结果，可以追问：它是不是来自这组输入和代码？如果改了训练日期、特征或代码，就不能把新结果装成旧实验的结果。模型文件、评分表、账户结果文件，也可以各自保存校验码，用于发现覆盖或混用。

**它不是每个星期的一张交易状态快照，也不是一种模型质量指标。**每周股票分数和持仓记录是另存的结果；一个固定训练的模型可以输出很多周的分数，不需要每周重新为它做一次人工“验收”。上述132列只是规划例子，完整132列模型仍未完成。

当前实现`digest()`就是分块读取文件，计算SHA-256；`content_id()`就是对排序后的配置JSON计算SHA-256。这不调用语言模型。对较大的行情文件重复读取会花磁盘时间，但算完通常只需要返回“匹配/不匹配”。不需要将全部文件或长校验码清单让多个代理反复阅读。

合理的保留方式是：真实实验固定版本并关联产物；读取边界核对所用版本；出现实际变更时重新验证受影响的部分。旧检查记录不能证明新内容，但不变的内容可以复用有效证据。

### 目前GitHub只有一个软件CI定义，分两个系统运行

已实际读取根目录`.github/workflows/ci.yml`。触发条件是push、pull_request或手动启动；分别在Windows与Ubuntu上执行：

1. 安装Python3.12和项目依赖。
2. 运行pytest自动测试，主要使用合成样本和临时数据库。
3. 构建wheel安装包，检查能否打包。
4. 运行配置模板命令，检查这个入口是否可用。

**它们检查软件安装、兼容性和已写测试，不在GitHub上训练真实行情模型，不证明策略赚钱，也不等于那两名代理的复核。**软件测试在计算机上运行；Token主要用在我发起工作、读取失败信息、理解问题、写修复和报告，以及代理复核这些内容时。等待程序本身的分钟数不是Token计数。

本地公开交付仓库已有56个提交。提交数不等于56次推送或56次CI，我没有把它们混算；但许多小交付仍会增加发布准备和观察成本，应该按可审阅的完整改动成批交付。
