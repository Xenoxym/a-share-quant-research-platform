# 组合公式首批实际执行：发现存储容量瓶颈，转入格式修复

2026-10-09 · E23 task-399bbf18fec9 · 本阶段没有新账户收益成果，接续建设。

## 实际发生了什么

第一项登记因为8GB预留加4GB空闲超过机器约10GB可用，未启动计算，取消并仍计名额。修订资源后第二项登记实际计算32个价量公式：13个保存成功，19个被输出预算挡住，整个作业按规则失败；没有把13个局部产物冒充一批成功，更没有拿它们挑赢家。筛选、新模型训练和新账户均为0。

## 为什么写不下

每个公式都重复写379842条样本编号、日期和股票。在第一个公式里，数值文件28,662,329字节，缺失文件25,346,292字节；两份样本编号列合计49,890,486字节。因此单个约54MB，主要花在重复索引。13份产物已约702MB，继续32份就超过750MB；本机当前可用磁盘约10.85GB，也不适合直接提高整批上限来支持上千公式。

原生公式计算部分约47.72秒，登记、冻结、监督等整case约183.83秒；采样全树峰值约1.31GiB、空闲最低约8.67GiB。这里的瓶颈是存储布局，不是账户收益、预测模型或内存不足。

## 接下来怎么改

同一批只保存一次股票/日期/样本编号；各公式保存按共同顺序排列的分数、时点和缺失原因。读回时还原完整表，让筛选照常使用。新格式必须显式版本化、保留旧格式读取，检查共同索引、行序、缺失、时点和文件身份；不能靠去掉校验来减少文件。

先做有限软件反例，确认旧格式兼容和读回一致，然后另立有限真实32公式容量验收。旧2登记和32次实际候选尝试永久保留，不退款、不改为成功。之后再完成广泛家族筛选及少数真实账户比较。

## 此前这段时间的路径

原12模型/32账户失败结论不变；完成分数头部诊断、日历序列接口、成熟训练目标与可加载模型接口、双平台CI。生成256公式元数据、准备32原料训练源并双复核，实际跑首批后发现上述重复索引瓶颈。模型保存接入注册worker、真实序列/神经模型、组合风险和其他研究路线继续保留，不把这一批手工组合当成完整自动Alpha发现。
